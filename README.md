## Project Overview

Snack Squad is a Flutter signup application built as part of MAD 4360 In-Class Activity 10. It demonstrates form validation, password confirmation, local password guidance, and a signup-tip interface with loading, success, and error states.

## Features Implemented

- **Signup form:** Full name, email address, password, and confirm-password fields.
- **Input validation:** Checks required fields, email format, minimum password length, and matching passwords.
- **Personalized success:** Displays a welcome message using the entered name after successful validation.
- **Password Coach (Task B):** Provides local password-length guidance.
- **Signup Coach (Task A):** Provides a signup tip through a deterministic mock service.
- **Loading and error handling:** Displays loading feedback and a friendly error with a retry option.
- **Offline testing:** Includes a control to simulate an unavailable signup-tip service.
- **Responsive layout:** Uses a scrollable layout that adapts to available screen space.

## AI Signup Coach: Implementation and Privacy

No instructor-provided AI endpoint was available, so this project uses a deterministic mock implementation. It does not call a live AI model or make a real HTTP request.

The mock service accepts the fixed task label `signup_tip` and topic `password_help`. The user's name, email, and password are not passed to the signup-tip service.

The displayed response is trimmed to a maximum of 240 characters. The mock is clearly labeled so that users can distinguish it from advice generated by a live AI model.

## Graduate Reflection

### 1. Identify one privacy or security boundary in the client-to-proxy-to-model flow. What threat does it reduce, and what risk remains?

In my implementation, the signup-tip service receives only fixed task and topic values. The name, email, and password are not passed to the service, which reduces unnecessary exposure of personal information. Since the implementation is a local mock, it does not currently have a proxy-to-model connection. A future live implementation would also need secure endpoint access, server-side controls, and protection against accidental disclosure of sensitive information.

### 2. How would you evaluate whether AI tips are useful, safe, and consistent?

I would prepare test cases covering short passwords, long passwords, password reuse, and requests for irrelevant or unsafe advice. I would check whether each response is relevant, understandable, safe, and consistent with the requested topic. Useful measurements would include the percentage of responses that pass the safety and relevance checks, the frequency of empty or invalid responses, and the rate of inappropriate advice. My current mock returns a predetermined tip, so it does not establish the quality or consistency of a real AI model.

### 3. Why must AI output be treated as untrusted data?

AI output should not automatically be trusted because it may be incorrect, irrelevant, or unsafe. In this application, the signup tip is displayed as plain text and limited to 240 characters. Form validators independently determine whether the user's input is acceptable, so the tip cannot approve or reject a signup. A live implementation should also validate the response format and provide a safe fallback when the response is invalid or unavailable.

## Design Trade-off and Limitation

The mock service makes the feature easy to test without exposing credentials or depending on network availability. However, it cannot demonstrate live AI integration or real network failure behavior. Connecting the instructor-provided HTTPS service and adding automated tests for response parsing, timeouts, and error handling would be useful next improvements.
